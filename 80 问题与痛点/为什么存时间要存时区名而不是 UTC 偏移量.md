# 为什么存时间要存时区名而不是 UTC 偏移量

## 痛点

从交易所导出两年的交易记录时，要选一种时间格式：带 `+08:00` 的写法，还是 UTC 写法。

看起来只是显示问题，实际上决定了这份数据以后还能不能回答「这笔交易那天对我是几号」。

顺带一个教训：AI 建议「导出选 `+08:00`，因为那是历史事实」。这个建议建立在一个未经核实的假设上——那两年一直在中国。实际横跨了中国、匈牙利、法国、德国等多地。**AI 会把自己的假设当成事实说出来，而且说得很有条理**；判断依据必须来自自己掌握的、AI 无从知道的信息。

## 以前怎么解决

直觉做法是把字符串里的 `+08:00` 当成时区存下来，觉得「记录了偏移量 = 记录了地点」。

不成立，三个理由：

1. **偏移量会在一年内变化。** `Europe/Budapest` 冬天是 `+01:00`，夏天是 `+02:00`，同一个地方两个值。
2. **偏移量倒推不回地点。** `+01:00` 可能是巴黎、柏林、罗马，也可能是拉各斯。
3. **时区规则会被政治决定修改。** 存了名字才能按新规则重新计算，存了结果就冻结成一个可能过时的值。

更根本的一点：从外部系统导出时，字符串里那个偏移量是**导出当天选的**，不是交易发生时的所在地。它是一层换算，不是一个事实。

## 技术演进

区分清楚两个词：

```text
+08:00          是 UTC Offset（偏移量），是结果
Asia/Shanghai   是 IANA 时区名，是依据
```

主流方案殊途同归——**瞬间与地点分开存**：

| 方案 | 做法 |
|---|---|
| Java `java.time` | `Instant` + `ZoneId` 组成 `ZonedDateTime` |
| JS Temporal | `Temporal.ZonedDateTime` |
| RFC 9557（2024） | `2026-08-20T05:40:32+08:00[Asia/Shanghai]` |
| PostgreSQL 社区实践 | `timestamptz` 存瞬间，再加一列存 IANA 名字 |

顺带解释一个误导性命名：PostgreSQL 的 `timestamptz` 会把时区扔掉，因为它存的其实是 [[Instant（瞬间）]]，不是 [[ZonedDateTime（带时区时间）]]。名字里的 `tz` 指的是「输入输出时做时区换算」，不是「保存了时区」。

至于已经发生的事件，偏移量基本不会变错：IANA 的规则变更几乎都面向未来。所以风险不是「以后会算错」，而是「当初有没有把地点记下来」。

一个数据结构解决不了的问题：**交易所只记录瞬间，从不记录地点，信息在源头就缺失了**。账本项目的补法是加一份行程区间表，用约 10 段行程反查地点，而不是逐笔标注 706 条交易。

## 我的理解

存偏移量等于**存结果、丢依据**。依据（地点名）能重新算出结果，结果算不回依据。

这和派生数据的道理是同一个：能算出来的东西不要当事实存，真正该存的是那个算不出来、只能被记录的事实——人当时在哪儿。
