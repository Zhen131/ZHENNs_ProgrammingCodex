# 为什么账户交易需要 nonce

## 痛点

去中心化网络里没有银行替你盯着，却要同时解决三件事：

1. 同一条签过名的 TX 不能被执行两次，否则别人拿你发过的 TX 反复广播，你的钱就被扣光。这叫 Replay Attack（重放攻击）。
2. 你的多笔 TX 要有确定的先后顺序。
3. 发错了、卡住了，要有办法替换。

## 怎么解决的

先看几种笨办法：

| 办法 | 问题 |
|---|---|
| 节点记住所有执行过的 TX，来一条就查一遍 | 存储无限增长，每个节点都得存全部历史，查询越来越慢 |
| 给每条 TX 一个随机唯一 ID | 本质上还要记住所有用过的 ID，问题和上面一样 |
| 给 TX 设有效期（时间戳） | 去中心化网络没有统一时钟，有效期内还是能重放 |
| 让一个中心机构发编号 | 违背去中心化 |

Solana 走的是另一条路：TX 带一个近期区块哈希当有效期，细节待确认。

[[Nonce（账户交易序号）]] 的做法：每个账户只存**一个整数**。它巧在几处：

- **一个数字压缩了整个历史。** 类比页码连续的账本：你知道"翻到第 5 页"，就知道前面五页都写过了，不用重翻一遍。节点判断一条 TX 能不能执行，只比较一个数字，存储量和历史长度无关。
- **顺序是白送的。** 4 之后必须是 5，5 之后必须是 6，不需要额外设计排序机制。
- **不需要时钟，也不需要全局协调。** 每个账户自己的计数器只有账户主人在用，不同账户之间完全并行，互不干扰。
- **它同时是槽位。** nonce 5 就是一个位置，同一个位置只放一条 TX，想换就用同一个编号发更高出价的，旧的被顶掉。Speed up 和 Cancel 靠的就是这个。
- **防篡改是顺便得到的。** nonce 在签名里面，攻击者改不了。

## 我的理解

用最小的代价（一个整数）同时解决去重、排序、可替换三件事。不是功能多，而是用得省。

代价也在同一个地方：顺序让它会队头阻塞，一条 TX 卡住，后面全卡。

这种"用一个状态值压缩历史"的手法在别处也出现。TCP 的 sequence number 做的是同样的事：让接收方知道哪些包收到了、哪些重复了、顺序有没有错。
