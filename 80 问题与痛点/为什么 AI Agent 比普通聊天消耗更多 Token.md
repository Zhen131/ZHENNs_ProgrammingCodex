# 为什么 AI Agent 比普通聊天消耗更多 Token

## 痛点

用户可能只说“修一下这个 Bug”，但 AI Agent 的用量却远高于一次普通问答。只计算用户手打的 Prompt（提示词），会漏掉真正进入模型的项目指令、文件、日志、工具结果、历史步骤和模型输出。

## 核心原因：一次任务包含多次模型调用

典型 Agent 工作流可能是：

```text
读取任务与仓库规则
  ↓
搜索并读取代码
  ↓
模型分析并调用工具
  ↓
读取测试或错误日志
  ↓
修改、验证、再分析
```

每轮调用都可能产生新的 [[Token（语言处理单位）|Input Token]] 和 Output Token。为了维持任务连续性，先前消息、计划、代码片段或工具结果还可能在后续调用中再次进入 [[Context Window（上下文窗口）]]，所以累计用量远大于最初一句话。

## 哪些因素会放大消耗

- 仓库、文件和日志规模大，且缺少定向搜索。
- 工具返回内容过长，后续回合又反复携带。
- 任务需要多轮尝试、测试失败和返工。
- 模型输出详细分析、补丁或长文档。
- 推理模型使用额外 reasoning token（推理 token）。
- 多 Agent 并行时，每个 Agent 都有自己的上下文与调用链。

## Cached Input 能解决什么

当多个请求重复使用相同的长前缀时，Prompt Caching（提示缓存）可能降低延迟和计费成本。它不会让 token 从用量统计中“消失”，也不能消除新增日志、修改后代码和后续输出带来的消耗。

## 如何更准确地观察与控制

- 看完整任务的累计用量，不只看用户 Prompt 长度。
- 区分 input、cached input、output 和 reasoning token，而不是只看 total。
- 让 Agent 定向搜索和分段读取，避免无差别加载整个仓库。
- 限制无关或重复的工具输出，并在长任务中压缩已确认的信息。
- 先缩小问题和验收条件，减少无效尝试与返工。

控制 Token 不是单纯追求“越少越好”。必要的代码阅读和测试日志能提高正确率，目标应是减少与任务无关的上下文和重复调用。

## 我的理解

Agent 的基本计量对象不是“用户发了几句话”，而是整个循环里模型累计处理和生成了多少 token。一句短指令可以触发很长的工具工作流。
