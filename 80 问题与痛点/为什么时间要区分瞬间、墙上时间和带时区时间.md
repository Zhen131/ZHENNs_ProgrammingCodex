# 为什么时间要区分瞬间、墙上时间和带时区时间

## 痛点

账本项目的交易列表里，两种日期格式并存：

```text
2026-08-28
2026-08-28T00:00:01+08:00
```

顺手写个函数取「这笔是哪一天」，问题就冒出来了。同一个时刻的两种写法：

```text
+08:00 写法 : 2026-08-20T05:40:32+08:00
UTC   写法 : 2026-08-19T21:40:32.000Z

是同一时刻吗？ true          ← 毫秒数完全相同

但取「哪一天」时：
+08:00 写法 → 2026-08-20
UTC   写法 → 2026-08-19    ← 差了一天
```

同一个瞬间、同一份数据，「哪一天」却不同。这说明「时间」这个词里至少藏了两个独立的东西。

## 以前怎么解决

最常见的做法是截取字符串前 10 位当日期：

```js
const date = trade.timestamp.slice(0, 10)
```

这行代码的隐患是：它让「哪一天」取决于**写的时候用了哪种表示**，而不是取决于那个瞬间本身。换个写法就换一天，而且没有任何报错。

## 技术演进

现代时间库（Java 的 `java.time`、JS 的 Temporal）的做法是把「时间」拆成三个类型，因为三种各自缺了别人有的东西：

| 类型 | 能排序吗 | 能答「几号」吗 |
|---|---|---|
| [[Instant（瞬间）]] | 能 | 不能 |
| [[Wall Clock Time（墙上时间）]] | 不能 | 能，但只是钟面数字 |
| [[ZonedDateTime（带时区时间）]] | 能 | 能 |

结论很直接：

```text
只要排序        → Instant 就够
只要钟面数字    → Wall Clock Time
两个都要        → 必须是 ZonedDateTime
```

而 ZonedDateTime 里的地点必须存 [[IANA Time Zone Database（IANA 时区数据库）]] 的名字，不能只存 [[UTC Offset（UTC 偏移量）]]，理由见 [[为什么存时间要存时区名而不是 UTC 偏移量]]。

「哪一天」不是数据自带的属性，而是 Instant 加地点算出来的 [[Derived Data（派生数据）]]。把它当成字符串前 10 位来保存，就是把派生结果当成了事实。

## 我的理解

我原来以为时间就是一个东西，`2026-08-20 05:40` 已经够了。真实情况是它至少是三个：**一个绝对时刻、一组钟面数字、一个观察地点**。

不是库设计得复杂，而是这三件事本来就互相独立，任何一个系统只要跨了地区，缺哪一个都会出问题。
