# 为什么前端页面不能长期依赖写死数据

## 痛点

写死数据可以让页面先长得像一个真实功能，但它本质上只是样板数据。页面如果长期依赖写死数组，用户操作不会真正改变业务结果，开发者也容易误以为链路已经跑通。

在账本项目里，写死的交易列表和资产汇总看起来像账本，但新增交易后页面不会自然更新，资产汇总也不是从真实交易和价格计算出来的。

## 以前怎么解决

早期开发常用写死数据搭页面骨架，这有价值：可以先确认 UI 结构、布局和基础样式。但当目标变成验证业务链路时，写死数据就会挡住真实问题。

真正要验证的是：

```text
用户输入
-> 表单草稿
-> 校验
-> 事实数据
-> 派生数据
-> 页面展示
```

## 技术演进

更合理的方向是让页面从真实 state 或真实数据源读取数据：

- 列表读取事实数据，而不是读取写死数组。
- 汇总、统计、持仓、预览这类结果作为 [[Derived Data（派生数据）]] 计算出来。
- [[React State（React 状态）]] 可以先承载页面运行期间的数据。
- 简单页面状态可以先用 [[useState（React 状态 Hook）]]；复杂核心业务状态可以进一步用 [[useReducer（React Reducer Hook）]] 集中管理修改规则。
- 后续如果需要长期保存，再接入 IndexedDB、后端数据库或其他持久化方案。

## 我的理解

写死数据适合搭样子，不适合验证功能是否真的工作。真正的业务页面应该让用户输入、事实数据、派生结果和页面展示沿着同一条数据链路变化。
