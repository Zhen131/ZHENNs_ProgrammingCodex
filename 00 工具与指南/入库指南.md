# 入库指南

> 给我自己和 AI 看的。怎么往「编程宝典」里存东西、怎么判断该不该存、存完怎么检查。
> 全部规则只有这一个文件 + 根目录 `CLAUDE.md`。

## 一、这个库是什么

它是我编程能力的**缓存**。学会一个东西，存成一张卡；以后忘了，搜一下就能直接用，不用重新推导。

所以一张好卡的标准只有一个：**半年后我忘光了，打开它 30 秒内能捡起来用。**

## 二、两种卡片

### 技术卡：一个稳定的概念

一个概念一张卡。概念要满足：离开当前项目依然成立，一年后大概率还会用到。

适合：`Closure（闭包）`、`Gradient Descent（梯度下降）`、`HTTP`、`Diode（二极管）`、`Unit Test（单元测试）`、`SCQA Model（SCQA 汇报模型）`。

不适合：
- 项目里的变量名、文件名、类名、服务名（`LedgerData` 不是概念，`Derived Data（派生数据）` 才是）。
- 一次调试的流水账。
- 一句话就能说完的东西——并进上位概念的卡里。

### 问题卡：一个"为什么"

从痛点出发，解释某个技术**为什么要存在**。一张问题卡通常链到好几张技术卡。

适合：`为什么 React 不能直接修改 state`、`为什么存时间要存时区名而不是 UTC 偏移量`。

不适合：
- `X 和 Y 是一回事吗` 这类两行能答完的辨析 → 写进技术卡的 `## 容易混淆` 小节。
- 标题绑死某个项目（"为什么账本页面不能…"）→ 把主语换成通用的（"为什么前端页面不能…"）。

### 素材：还没消化的

原始转录、摘录、临时笔记放 `90 素材与临时笔记`，frontmatter `type: 素材`。消化成卡片后，素材可以留着当原文参考，但卡片里要链回素材，素材里要链到卡片。

## 三、放哪

技术卡按领域放 `10`–`70`，问题卡**全部**放 `80`，素材放 `90`。各文件夹放什么见 `CLAUDE.md` 的表。

拿不准就放最接近的。文件夹只负责"找得快"，知识之间的关系靠链接。

## 四、命名与语言

- 技术卡文件名：`English Term（中文）.md`，例：`Virtual DOM（虚拟DOM）.md`。专有名词没有通用中文译名的可以只写英文：`WordPiece.md`。
- 问题卡文件名：中文问句，不带问号：`为什么需要 JSX 或 TSX.md`。
- 正文：中文讲逻辑，英文定术语。术语第一次出现写 `English（中文）`，之后直接英文。代码、命令、报错、库名不翻译。
- `aliases` 要写全：英文全称、缩写、常见中文叫法。以后搜的时候靠它。

## 五、frontmatter

```yaml
---
type: 技术卡片        # 技术卡片 / 问题卡片 / 素材
status: 草稿          # 草稿 / 已校
aliases: [Gradient Descent, GD, 梯度下降]
created: 2026-10-08
updated: 2026-10-08
tags: [语言/Python]   # 可选，见下
---
```

- `status` 的含义是**缓存有没有被我验证过**：
  - `草稿`：AI 写的或我还没仔细读过。能看，但别全信。
  - `已校`：我亲自读过、认可、改过。可以直接当缓存用。
  - **只有我能改成 `已校`。** AI 入库的卡永远是 `草稿`。
- `tags` 可选，只用于文件夹表达不了的横切维度：`语言/JavaScript`、`主题/密码学`、`问题/前端架构`。不要打跟文件夹重复的 `领域/xxx`，不要打 `类型/`、`层级/`、`状态/`。

## 六、模板

在 Obsidian 里 `Cmd+T`（插入模板）选 `技术卡片` 或 `问题卡片`。模板文件在 `00 工具与指南/templates/`，AI 入库时也从那里读结构。

各节怎么写：

**技术卡**
- `一句话`：必填。这就是缓存值本身。
- `背景：它出现前的问题`：它出现前人们怎么做、哪里痛。写不出来就删这一节。
- `核心机制`：必填。能放最小可跑例子最好。
- `典型使用场景`、`局限性`：有就写。
- `容易混淆`：可选。放 "X 和 Y 是不是一回事" 的辨析。
- `关联`：必填，至少 1 条，**每条写清关系**，不要只贴链接。
- `进一步理解`：旧卡被新材料加深时追加，一条一句。

**问题卡**
- `痛点`：必填。没这个技术时具体卡在哪。
- `怎么解决的`：必填。哪些技术解决了哪部分，正文里直接 `[[链]]` 到技术卡。
- `我的理解`：可选。
- `关联`：必填。

节不够用可以加，用不上的可以删。**模板是下限不是上限，别为了填满而注水。**

## 七、入库五步

1. **读懂材料。** 找出：学到了什么概念、背后的真实问题、是在什么项目/什么 bug 里学到的。
2. **先搜。** 英文名、中文名、缩写、同义词各搜一遍。已有相近卡 → 更新它，不要新建。
3. **判断动作。**
   - 稳定概念，没有旧卡 → 新建技术卡。
   - 有清晰痛点 → 新建或更新问题卡。
   - 一句话能说完 → 并进相关技术卡。
   - 还没消化好 → 放 `90`，`type: 素材`。
4. **建链接。** 新卡正文里第一次提到已有概念就 `[[链]]`。被加深的旧卡要反向链回来。
5. **检查。** 跑 `python3 "00 工具与指南/check.py"`，零 ERROR；再过一遍下面的清单。

## 八、入库清单

每张新卡过一遍：

- [ ] 它离开当前项目依然成立吗？
- [ ] 它是不是已有某张卡的一段内容？（是 → 合并）
- [ ] 标题够通用吗？有没有绑死项目？
- [ ] `一句话` 能让半年后的我 30 秒捡起来用吗？
- [ ] `关联` 至少 1 条，每条说清了关系吗？
- [ ] 被加深的旧卡反向链了吗？
- [ ] `aliases` 把常见叫法写全了吗？
- [ ] 不确定的内容标了"待确认"而不是写成事实吗？
- [ ] `check.py` 零 ERROR 吗？

清单过不了的，按严重程度处理：**删除**（没复用价值、项目专属、编造的）> **合并**（旧卡能装下）> **改名**（标题太窄）> **退回素材**（还没消化好）。

写完就不想删，是知识库变臃肿的唯一原因。删错卡和建对卡一样重要。

## 九、长期维护

- 一个文件夹超过约 40 张、且明显分成两类主题时再拆，拆完更新 `CLAUDE.md` 的表。不要提前拆。
- 隔一段时间打开根目录的 `学习历程.base`，看"还没校读的"那个视图，把读过认可的卡改成 `已校`。
- 规则变了只改这一个文件和 `CLAUDE.md`，不要再长出第三份规则。
