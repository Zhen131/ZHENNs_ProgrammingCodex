# 编程知识入库审查指南

> 用于 `编程宝典` 的入库后自我审查。
> 目标不是多产出文件，而是保持知识库轻、准、可复用。

## 一、审查目标

每次入库完成后，AI 必须在提交前做一次审查，判断新增和修改内容是否真的值得留在知识图谱中。

审查重点：

- 防止把项目专属对象误升格为通用技术卡片。
- 防止 AI 幻觉制造不存在或不稳定的概念。
- 防止新增低复用、低关联、低信息密度的卡片。
- 防止重新制造索引、MOC、项目学习记录等中转层。
- 防止卡片虽然有链接，但链接关系不能真正帮助理解。

审查不是格式检查。格式正确但没有复用价值的文件，也应该删除、合并、改名或退回素材。

## 二、严重级别

### P0：入库事故，禁止提交

出现 P0 时，必须立即停止提交，先修复。

典型情况：

- 编造不存在的技术、概念、API、文件或项目事实。
- 把不确定内容写成确定事实，且会误导后续学习或开发。
- 删除、覆盖用户已有重要内容，且用户没有明确要求。
- 引入隐私、密钥、账号、私人路径等不应入库的信息。
- 批量破坏 wikilink、frontmatter 或既有图谱结构。

处理方式：

- 删除幻觉内容。
- 恢复被误删内容。
- 把不确定内容改为 `待确认` 或退回 `90 素材与临时笔记`。
- 修复断链后重新审查。

### P1：严重图谱污染，必须本次修复

P1 不一定是事实错误，但会让知识库变臃肿、变杂，必须在本次入库内处理。

典型情况：

- 把项目专属对象当成通用技术卡片。
- 新建只有当前项目能用、其他项目基本不会复用的卡片。
- 重新制造索引、MOC、聚合式学习文件或项目学习记录中转层。
- 为了保留材料而强行拆出一批弱概念、弱连接的文件。
- 已有旧节点能承载，却重复造一个近似概念。

反例：

- `LedgerData（账本数据对象）` 是账本项目里的对象名，不是跨项目稳定概念。它不应该作为技术卡片长期存在。应该把其中可复用部分抽象到 [[Derived Data（派生数据）]]、[[React State（React 状态）]] 或数据建模问题卡里。

处理方式：

- 删除项目专属技术卡。
- 将项目语境压缩为技术卡或问题卡正文中的例子。
- 把专属标题改成通用标题。
- 合并重复节点。

### P2：结构质量问题，应优先本次修复

P2 会降低图谱质量，但通常不至于立刻污染整个知识库。

典型情况：

- 标题过度绑定项目，例如“为什么账本页面不能...”而不是“为什么前端页面不能...”。
- 技术卡和问题卡边界混乱，问题卡在讲概念定义，技术卡在讲个人经历。
- 卡片粒度过细，一句话能说清却单独成卡。
- 内容主要是某次学习流水账，没有抽象成稳定概念或真实痛点。
- 项目例子占比过高，压过了通用机制。

处理方式：

- 改名为更通用的问题或概念。
- 删除流水账段落，只保留能解释机制的项目证据。
- 合并到更上位的技术卡。
- 把不成熟内容退回素材区。

### P3：表达与连接问题，可本次修复或列为待补

P3 不影响是否能入库，但影响未来阅读效率。

典型情况：

- `## 关联` 有链接，但关系解释太弱。
- 正文里关键概念没有第一次出现就加 wikilink。
- 英文术语和中文翻译不统一。
- `aliases` 不完整，未来搜索不方便。
- 例子太单一，但概念本身值得保留。

处理方式：

- 补充直接链接。
- 调整术语和别名。
- 增加一两个跨场景例子。
- 在审查报告里列为后续待补。

### P4：轻微修饰，可以顺手处理

P4 是不影响图谱健康的小问题。

典型情况：

- 语句不够简洁。
- 段落顺序可读性一般。
- 标签可微调。
- 例子措辞可以更贴近 Ethan 的理解方式。

处理方式：

- 顺手改，不要扩大成重写。
- 如果会分散本次任务，可以不处理。

## 三、每张新增卡片必须回答的问题

新增卡片前后都要问：

1. 它是否是跨项目可复用的稳定概念或真实痛点？
2. 它是否比已有节点更独立，而不是已有节点的一段内容？
3. 它是否能和至少一个技术卡、问题卡形成直接关系？
4. 如果删掉它，知识库会不会损失重要理解？
5. 它的标题是否足够通用，而不是只描述当前项目？

如果这些问题大多回答不上来，不要保留为独立卡片。

## 四、项目语境的处理规则

项目语境有价值，但不能自动变成项目对象卡。

可以保留：

- 用项目例子解释通用概念。
- 用项目痛点引出问题卡。
- 在技术卡中写“在项目中的表现”式的短段落。

不应保留：

- 只在当前项目存在的类型名、变量名、文件名、服务名。
- 只复述本次开发流程的流水账。
- 只有当前项目能理解、离开项目就没有意义的卡片。

判断口径：

```text
项目对象不是技术概念。
项目经历不是中转层。
项目例子只能服务于通用理解。
```

## 五、审查动作

审查后按问题严重程度处理：

- 删除：没有复用价值、误建、幻觉或项目专属的卡片。
- 合并：内容可以被已有卡片承载。
- 改名：标题太项目化或太窄。
- 泛化：保留项目例子，但把主语换成跨项目概念。
- 退回素材：材料还不成熟，暂不沉淀成卡片。
- 标记待确认：事实不确定，但暂时有学习价值。

不要因为文件已经写完就保留它。维护知识库时，删除错误节点和新建正确节点同样重要。

## 六、提交前审查报告

每次入库提交前，AI 应在最终报告或提交前说明中给出简短审查结论：

```text
审查结果：
- P0：无
- P1：无 / 已删除 xxx
- P2：已将 xxx 改名为 yyy
- P3：待补 xxx
- P4：未处理
```

如果存在未处理的 P0 或 P1，不允许提交。

如果存在未处理的 P2，需要说明为什么暂不处理。

## 七、最低验证

审查之后至少验证：

- `rg` 检查已删除或改名节点没有残留引用。
- 本次新增/修改文件的 wikilink 目标存在。
- `git diff --check` 没有格式问题。
- `git status --short --branch` 能说明工作区状态。

全库模板文件里可能存在示例 wikilink，占位链接不等于内容断链。必要时优先对本次新增和修改文件做 targeted wikilink 检查。
