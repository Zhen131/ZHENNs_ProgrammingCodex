# ZonedDateTime（带时区时间）

## 一句话

`ZonedDateTime（带时区时间）` 是 [[Instant（瞬间）]] 加上地点，是唯一能同时回答「谁先谁后」和「那天对我是几号」的时间形式。

## 背景：它出现前的问题

[[Instant（瞬间）]] 能排序但答不出日期，[[Wall Clock Time（墙上时间）]] 有日期但不能排序。业务里这两个问题经常同时出现：交易列表既要按时间排序，又要按「哪一天」分组统计。

只用其中一种，总有一个问题答不了；而把两者胡乱混在一个字段里，就会出现同一笔数据换个写法就换了一天。

## 它解决了什么

它把两块信息显式地放在一起：

```text
谁先谁后？   → 用 Instant 比
那天几号？   → 用地点换算
```

地点一旦被写进数据，「哪一天」就变成一个可以重新计算的问题，而不是一个取决于当初字符串怎么写的偶然结果。

## 核心机制

地点必须存 [[IANA Time Zone Database（IANA 时区数据库）]] 的名字（`Asia/Shanghai`、`Europe/Budapest`），不能只存 [[UTC Offset（UTC 偏移量）]]。

序列化上，2024 年发布的 **RFC 9557** 把地点名直接写进时间字符串，并且向后兼容 RFC 3339：

```text
2026-08-20T05:40:32+08:00[Asia/Shanghai]
└──────────┬─────────┘└─┬──┘└─────┬─────┘
       墙上时间        偏移量      地点名
```

解析零依赖：去掉方括号那段，剩下的就是标准 RFC 3339 字符串，直接 `Date.parse` 即可（项目里实测通过）。浏览器新标准里 `Temporal.ZonedDateTime` 的 `toString()` 输出的正是这个格式。

存储上还有一条等价路径：**分两列存**，一列 Instant，一列 IANA 名字。这也是 PostgreSQL 社区在 `timestamptz` 之外的标准做法。

```text
Java 的 java.time
JS 的 Temporal
RFC 9557
PostgreSQL 社区实践

四条路给的是同一个答案：瞬间与地点分开存，再组合
```

## 典型使用场景

- 交易、订单、日志：既要排序，又要按「本地哪一天」归属。
- 跨时区团队的会议时间展示。
- 用户可见的时间格式化：同一个 Instant 对不同用户显示不同。

## 局限性

**数据源不给地点，数据结构补不了。**

交易所导出的记录只有 Instant，加上导出当天选的那个偏移量；它从来不记录「下单时人在哪儿」。信息在源头就缺失了，任何时间类型都变不出来。

账本项目里的补法不是改类型，而是补一份外部事实：用**行程区间表**记录约 10 段行程（哪段时间人在哪个时区），再按 Instant 落在哪段区间去反查地点，而不是逐笔标注 706 条交易。

## 和其他概念的关系

- [[Instant（瞬间）]]：ZonedDateTime 的绝对量部分。
- [[Wall Clock Time（墙上时间）]]：ZonedDateTime 展示出来的那一面。
- [[UTC Offset（UTC 偏移量）]]：只是渲染结果，不能替代地点名。
- [[IANA Time Zone Database（IANA 时区数据库）]]：提供地点名和换算规则。
- [[Derived Data（派生数据）]]：偏移量和「哪一天」都是从 Instant + 地点算出来的，属于派生数据。
